## Data gaps (items 6, 8, 10)

### 6 - Source name colors (Drops from)

The color has nothing to do with the creature itself. modules/ItemSearchCells.lua:218-225 (sourceCell) paints every named NPC row `tone="red"` and every object row `"plain"`. A container row gets its item quality, and an unnamed row is muted. This comes from the feedback spec, docs/2026-11-25-ITEM_SEARCH_FEEDBACK/03_SPEC.md:166: "creatures in the hostile color, objects and containers in white". So red only means "this is a creature", which the Type column already says. It is also misleading, because many creature drop sources are friendly town NPCs. Measured over every NPC that appears in ForeverDB.drop (5824 ids): nfac=A 489, H 314, AH 560, nil 4461. On Peacebloom 6 of 43 drop NPCs carry a side; on Linen Cloth it is 60 of 381. Kogan Forgestone (1245, A), Lisan Pierce (1414, A), Adam Lind (12658, A), Tamara Armstrong (2361, A), Rejold Barleybrew (1374, A) and Takar the Seer (6244, nfac=A) are faction NPCs whose MaNGOS loot tables (src mask 58 = vmangos+pfquest+client+att) only pay out when the other side kills them. Rank data also exists: drop NPC rank 0 = 3438, 1 elite = 1457, 2 rare elite = 124, 3 boss = 95, 4 rare = 287, and 423 have no npc row.

**Options:** A (recommended): reaction color from nfac against the player's side, like the game's unit-name colors. Your own side or AH (both): green (friendly, so it only drops if the other faction kills it; add an "other faction only" hint in the tooltip and maybe rank it last). Other side alone: red. No nfac (nil, which is mostly hostile mobs): yellow or red as hostile. This reuses IS.OtherSide-style logic. B: color by rank (rare = silver, elite = gold, boss = orange or purple, normal = white). It overlaps the Type column, which already shows rank. C: drop the special color and use plain white, since Type says creature or object. A + C hybrid: white for normal hostile mobs, green or red only for faction NPCs. Whichever is picked, update spec §166.

### 8-price - Sold by Price '–'

ForeverDB has no buy price for these vendors. The window's price comes from facts.vendorPrice = db.VendorPrice(itemID) (modules/ItemSearchModel.lua:331-332). VendorPrice reads `vend[item]` and then `vp[npc][item][1]` (libs/LibKa0s/ForeverDB.lua:392-405). The Cells layer shows that price only on the row of the vendor it was seen at (ItemSearchCells.lua:315-318), and Tip.lua:218-223 does the same. `vp` holds just 32 vendors and 443 vendor-item prices, so only 218 of the 3933 vended items have any price. 1313, 3490 and 3548 have no vp row and no vendx row. `vendx` (6 vendors, 60 entries, shape {[item]={s=,p=}}) also has a `p` price, but the adapter does not read it. The item row (`item[2447]`) carries no buy or sell price: its positions are name, quality, reqLevel, nil, class, subclass, invType, icon. So a dash is the honest answer today: no price is recorded for any of these vendors.

**Options:** A (recommended): record prices ourselves. On MERCHANT_SHOW, GetMerchantItemInfo gives an exact price per vendor and item. Store it in DropWatcher's SV as "seen" and prefer it over vp. Over time this fills in the vendors you visit. B: have the adapter also read `vendx[npc][item].p`, which is cheap but adds only 60 entries. C: a fallback estimate from GetItemInfo's sellPrice (the buy price is often about 4x that) marked as "~est.". It is not reliable, so it is not recommended without a marker. D: change the dash to a clearer "not recorded" and say so in the column tooltip.

### 8-cantbuy - "can't buy" and the faction letters

The data and the code are both correct, and Selina Weston is not a bug. ForeverDB nfac: 1313 Maria Lumere = "A", 3490 Hula'mahi = "H", 3548 Selina Weston = "H". Selina Weston is the Forsaken alchemy and herbalism vendor in Brill (spz map 1420 Tirisfal Glades; spw continent 0, about 2330,242). She is not in Southshore; the Alliance vendor there is someone else. The code: IS.OtherSide (modules/ItemSearchModel.lua:590-604) returns true when the vendor's nfac string does not contain the player's letter. The player's letter is "A" or "H" from UnitFactionGroup (core/CompatSearch.lua:68-75), and the function returns false when the side is unknown or the vendor's nfac is nil. FactionCell (ItemSearchCells.lua:298-303) then prints "can't buy" in red, or else Alliance, Horde or Both. So for an Alliance character the screen reads Maria = Alliance and the two Horde vendors = can't buy, which is correct. What the letters mean: nfac is ForeverDB's per-NPC side, "A" = Alliance, "H" = Horde, "AH" = both (neutral, e.g. goblins or Cenarion), and nil = not stated. The whole-database split is A 2512, H 1755, AH 3298, out of 7565 rows against 15831 NPCs. "can't buy" means the vendor serves only the other faction, so you cannot buy from them; the "Only my faction" filter hides those rows (ItemSearchTabs.lua:80). Side note: Takar the Seer (6244) is marked nfac=A in the data. Worth a sanity check, but it does not affect vendors.

**Options:** Keep the logic. Clarity options: (a) say "Horde only" or "Alliance only" in red instead of "can't buy", since naming the other side explains why; (b) put the faction icon next to the text; (c) add a column tooltip line: "A = Alliance, H = Horde, Both = neutral; red = only the other faction can buy here".

## Gathering nodes (item 7)

### 7a. What ForeverDB holds for objects (obj, odrop, spw, skill tables)

obj (ForeverDB/ForeverDB.lua:15849, 12,111 rows) has exactly ONE field, the name. 12,019 rows are {name} and 92 are empty {}. There is no type, lock, displayId or skill field, and ForeverDB_Full has no obj table at all. odrop (ForeverDB_2.lua:11067, 3,762 rows) is keyed by ITEM, as flat pairs objectId, chance x100 (10000 = 100%). It holds 38,373 pairs over 1,261 distinct objects, 1,251 of them named and 10 unnamed. Object positions are in spw under the key "o<id>" (for example o1618). The skill and lock tables exist but are EMPTY: meta.counts says fish=0, oskill=0 and osummon=0, and ForeverDB_4.lua:1457/1807/2235 declare D.fish, D.oskill and D.osummon with no rows. So ForeverDB has no gathering type and no required skill. The useful signal is on the ITEM row: fields 5 and 6 are class and subclass. Peacebloom 2447 is 7/9 (Herb, ForeverDB.lua:41394) and Copper Ore 2770 is 7/7 (Metal & Stone, :41685). wow-tools under /mnt/g/.../wow-tools holds only owner utilities (ace3-profile-manager, sv-browser and so on), with no DB2 or CSV, so there is no client GameObject or Lock data to use. The adapter reads the name only: libs/LibKa0s/ForeverDB.lua:281-289 (lib.Object, minor 3) says that positions past the name are not read.

### 7d. How Drop Watcher merges objects today and what 'Object x3' means

modules/ItemSearchModel.lua:155 IS.MergeNamedObjects collapses objects that share a NAME into the first row. It keeps the highest chance (it does not sum them) and stores every object id in `ids`. It runs only when there are 2 or more named objects (:328). The Type cell at modules/ItemSearchCells.lua:211-212 then reads L["Object ×%d"] with #ids, and the row tooltip at :234 says '%d kinds of %s'. For Peacebloom, 'Peacebloom, Object ×3' is three object ids named Peacebloom: 1618 and 3724 (100%, both with spw positions) and 657382 (0%, a Forever id with no position). The map spots are the union of the ids (ItemSearchCells.lua:167). 'School of Fish' is 180184, the data quirk above. The chests in the same list (Tattered or Battered Chest 2844-2849, 106318/9, Alliance Chest 111095, Dented Chest 626752) correctly remain drops.

### 7e. ItemTree's approach (described, not quoted)

ItemTree keeps gathering apart from drops in two places. (1) Its shipped Classic Era table already sorts each object source into a category. ItemTree/Core/EraSources.lua:336-346 maps herb to the group 'Gathered from', vein to 'Mined from', fished to 'Fished in' and any other object to 'Found in'. Per EraSources.lua:104-118 and :350-365, each herb or vein is drawn as ONE node row that carries the chance and opens onto its zones ('Gathered in' / 'Mined in'). The classification comes from its offline pipeline, not from in-addon heuristics. (2) For the player's own loot records, Core/Collector.lua:164 files a gather interaction under 'Gathered from'. Because the client reports opening a chest as a gather, :184-199 moves an object whose name contains a whole word from a container word list (chest, crate, barrel, footlocker, strongbox, cache, lockbox, coffer, trunk) to 'Found in'. Catches are filed by zone as 'Fished in', never 'from the Fishing Bobber' (:2496, :5053-5069). Skinning is its own 'Skinned from' group (:180).

## ItemTree badge (item 14)

### ItemTree verdicts (what exists)

ItemTree has no 'Toss' verdict: grep finds the word nowhere in ItemTree. Its verdict is a row of action TAGS, always in the order [Keep] [Auction] [Vendor]. Disenchant takes Auction's place for an enchanter. Core/Keep.lua:7640-7660 defines TAG_KEEP, AUCTION, VENDOR, DISENCHANT, WORTHLESS, EQUIP (an upgrade you can wear now; counts as a Keep) and PET (one stack of hunter pet food; counts as a Keep), plus OPEN and USE ('do this now' tags, 15186-15190). The state words the API reports are keep, vendor, sell, worthless, keepDisenchant and disenchant (Keep.lua:7567-7572). Keep.TagWord at Keep.lua:15094-15131 gives the labels: 'Keep (N)', 'Equip (specs)', 'Pet food', 'Auction', 'Disenchant', 'Open', 'Use', 'Worthless', 'Vendor'.

### ItemTree inputs and decision order

The order is in my own words from the Keep.lua:1-160 header and the numbered rules at Keep.lua:~7585-7638. (1) The player's override comes first: Always, Never or Off. (2) KEEP when any of these holds. The item has uses still ahead of the player, read from the item graph's down edges (reagent, tool, teaches, opens a lock, quest needs or starts it). A use counts as current when its level is unknown, at or above ENDGAME=50, or no more than BEHIND=10 levels below the player (Keep.lua:167-169). Two or more current uses keep the item. So do one endgame use, a current class-spell reagent, one use on an item of OWN_LEVEL 45 or higher, or any current quest use. Uses that do not count: recipes of professions the player lacks, quests for the other faction, and completed or abandoned quests. Also KEEP: the profession levelling route still needs the item, a stat or spec gear upgrade (or one wearable within the level window), a likely disenchant result that is itself a Keep, food for the player's level, or a profession consumable at the player's rank. One damper: an item sold by 5 or more vendors for 5 silver or less (EVERYWHERE_VENDORS/CHEAP_COPPER, :175-176) is neutral and never auctioned. (3) SALE, via auction-addon prices (Auctionator, TSM and others, read through Core/Prices.lua) with the vendor sell price as fallback. Auction is never offered for a bound or quest item, and never for grey, soulbound or plain-white gear with no use. A single item priced at 500g or more is a 'legendary' Auction (:7659). Auction must beat the vendor price by a Bar setting after the AH cut. A money test also applies: a full stack must reach max(1% of carried gold, 1s) (:7666-7667). Within 2x of the vendor value, both Auction and Vendor show (:7668). With no auction data, Auction and Vendor show with '(No AH data)'. Disenchant needs Enchanting and must clear the same Bar. (4) WORTHLESS: no vendor price, the AH cannot take it, and no use.

### ItemTree: what the number next to Keep is

It is not a score. It is the count of the item the Keep holds, the 'amount required' (owner ruling quoted in the comment at Keep.lua:10322-10349; computed by Keep.KeepCount at Keep.lua:10350). It is the sum of up to three needs. First, how many the player's profession levelling route still needs (Keep.ReagentKeepNeed :8978, Keep.KeepNeed :9036, which adds open quests; example in the code: 'Level First Aid (40 / 78 needed)' holds 78). Second, the open quests' need ('Westfall Stew (9 / 8 needed)' holds 8). Third, what carried supply crates take ('Waylaid Supplies: Peacebloom needs 20'). So 'Keep 122' on Linen Cloth and 'Keep 108' on Peacebloom are almost certainly the remaining route needs for Tailoring/First Aid and Alchemy (not verified against the owner's saved state). The count appears only for a use-rule Keep, never for Always, worn gear, a spare bag or a tool. When more are held than needed, the first sale tag carries the surplus, for example [Keep|20] [Auction|40] (Keep.SplitTags :10292-10320).

### ItemTree confidence tiers

Core/Confidence.lua:1-10 and 23-28 define six tiers, ranked at :47-55: verified=5 (the collector saw it on this client and build), mined=4 (read from this build's client DB2 tables), curated=3 (hand-maintained notes), baseline=2 (imported, not yet seen on this client), predicted=1 (rule-based, such as disenchant bands, always shown with a %) and guess=0.5 (the model's guess; never a step in a chain). When two facts disagree, the higher rank wins (Confidence.Best). The tiers are per FACT and drive small badges beside rows (UI/Badges.lua). Mined gets no badge because it is the norm (:60-67). Labels include 'Verified by collector, build X' and 'Imported baseline, unverified'. Imported rates are hedged as 'about 3%' and Era figures as '~12.5%'. The Keep verdict does not carry a confidence of its own. What it has instead: guessed edges never count, predicted edges count fully (Keep.lua:12-15), and 'Not enough AH data' is the one verdict-level hedge (Keep.SettleTie :10377).

### ItemTree badge drawing and placement

The tags are pre-rendered pill art in Art/keep-tags.tga (UI/Assets.lua:295-320; large 148x56 and small 96x34 source rects). The art is white and grey, so it is tinted at draw time: fill, a slightly darker outline and near-black lettering, all in one colour. Each pill is drawn as an inline texture escape TAG_SIZE=17 px tall (Keep.lua:15192). The Keep pill has a padlock icon left of the word. Tints: Keep/Equip/Pet use the player's Keep colour, default #3DDC84 green (UI/Theme.lua:140). Auction uses the Valuable colour, #FF8000 orange (:149). Vendor is grey {0.59,0.60,0.63}, Worthless a darker grey {0.40,0.40,0.42}, and Disenchant purple {0.64,0.44,0.88} (Keep.lua:15193-15194). Legendary Auction is full-colour untinted art. The counted Keep is one pill in two segments: the Keep segment with a square right edge, then a number segment with a dark divider down its left edge. Numbers 1-99 and '999+' sit on one sheet, and 100-999 on ten lazily loaded sheets (Keep.lua:15284-15343, Art/keep-count*.tga). Placement: the tag row is always the section's first line (UI/Tooltip.lua:4355-4362). That first line is drawn with AddDoubleLine and the label 'ItemTree' at the right in the muted grey (Tooltip.lua:143-146, 7985-7997). Reasons follow one per line, then summary lines, then the hint.

### Proposal: Drop Watcher verdicts and badge

Badge line: the first line of DW's tooltip block, drawn with AddDoubleLine. Left: 'Drop Watcher' in the tooltip label tone (mutedGold), replacing today's 'Drop Watcher · Item Search' title. Right: the badge, per the owner's swap. Badge = icon escape + word + score, as one tinted pill-style string. The tooltip face cannot draw glyphs, so it uses TipMarks-style texture escapes. Verdicts (original wording and logic): KEEP (dw.upgrade green, ph:lock): the score reaches the keep bar. HOLD (dw.sidegrade yellow, ph:hourglass, already vendored): a weak or future use, between the bars. SELL (gold, ph:coins): no meaningful use and a client sellPrice above 0. A gear item keeps DW's existing Evaluate verdict: an upgrade is a Keep, and the badge reads the kernel rather than re-deciding. A new collectible is a Keep at 100.

### Proposal: 0-100 keep score (explicit inputs)

Score = clamp(sum, 0, 100), from pure inputs DW already has, plus one Compat addition (sellPrice and bindType). +60: a quest in your log needs it (quests.state=='log'). +35: an available quest (state 'todo', mask allows, quest minLevel <= level+3) needs it. +50: startsQuest not yet done. Done quests add 0. Crafting, for recipes in a profession you HAVE, summed and capped at +50: known recipe orange +30, yellow +20, green +8, gray 0; an unlearned recipe of your profession with rank below gray +10. Recipes of professions you lack add 0, but each one adds +3 toward 'sellable to others', capped at +9. A new collectible (Collectibles newCollect) scores 100. A gear upgrade (Evaluate) is +70, a sidegrade +20. Dampers: -20 when the item is re-buyable (vendors >= 3, or any vendor at ForeverDB vendorPrice <= 5s); -15 when every use is gray or done. Grey quality is never above 15 unless a quest needs it. Bars: Keep >= 50, Hold 20-49. Below 20: Sell if sellPrice > 0, else Toss. The number on the badge is the score, and the tooltip's reason lines name the top 1-2 contributors (for example 'In your log: Westfall Stew', 'Leatherworking skill-up (orange)'). Optional and closer to ItemTree's idea: when a quest in the log carries a count, show the count instead. DW has no quest counts today, so the score is the honest number.

### Proposal: confidence measure

Confidence answers 'how many of the inputs the score needs were actually answered'. It is not the score itself. Each input has a weight: quest state 3, recipe known/rank 3, ForeverDB loaded 3, client item cached (quality, sellPrice, bind) 2, gear evaluated 2 (equippable only), drop and vendor facts present 1. Confidence = answered weight / needed weight x 100, with tiers High >= 80, Medium 50-79, Low < 50. These items lower it: ForeverDB 'missing'/'loading' (no quests, vendors or drops; crafting still comes from the shipped table); item not cached (no sellPrice, so Sell versus Toss is unknown); profession ranks unread (the profession window was never opened, so recipe colours are nil); Pawn 'pending'. Show it as three small pips after the score, or as a muted suffix on the badge's hover line, such as 'Confidence: Medium — open your profession window to rank recipes'. A Low confidence never shows TOSS; it falls back to HOLD, so the addon never tells a player to delete something it could not judge. Everything stays pure and testable like IS.Rank, as a new IS.Verdict(facts, me) answering { verdict, score, confidence, tier, reasons }. ItemTree code is not ported: only the concept of a first-line tag with the addon label opposite carries over.
