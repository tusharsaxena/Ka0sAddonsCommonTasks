# #91 Survey where wago.tools DB2 lookups can validate Ka0s addon data sets and assumptions

## What

Survey the Ka0s collection for data sets and hard-coded assumptions that could be checked against the game client's own data on [wago.tools](https://wago.tools). Then decide whether the download, cache and bundle plumbing should be shared instead of rewritten in each addon.

AuraMaster already does this for its spell categories (`tools/spell-research/`, AuraMaster #27). ConsumableMaster and KickCD each have an issue to do the same for their seeds.

## What wago.tools gives us

- `https://wago.tools/api/builds`: builds per product (`wow`, `wowt`, `wowxptr`, `wow_beta`, `wowf`).
- `https://wago.tools/db2/<Table>/csv?build=<build>`: every DB2 table as CSV for one build: spells, effects, mechanics, cooldowns, items, item effects, currencies, maps, instances and difficulties, specs, talents, skill lines, and so on.

## Questions

1. **Inventory.** Which addons carry seeded ids or assumptions that DB2 could confirm? For example: spell, item, currency, instance, map or difficulty ids; spec and class tables; the LibKa0s `Compat` per-client assumptions (does an API-backed table, enum or constant exist on a given client build); interface numbers per product.
2. **Shared tooling.** Should a small stdlib Python helper (resolve build, fetch with a proper User-Agent, cache per build, freeze raw CSVs into a dated bundle, replay offline, rulings-as-data) live in one place? Options: LibKa0s `tools/`, dev-copilot, or WowAddonStandards (as a reference implementation). Each addon would keep only its own rules.
3. **Kit integration.** Is anything worth checking from the headless test kit (for example a frozen DB2 snapshot fixture), or does this stay entirely outside the green gate (testing-§7, measurement runners)?

## Outcome

A short written finding: which addon checks what, plus a decision on where the shared helper lives. File follow-up issues in the affected repos.
