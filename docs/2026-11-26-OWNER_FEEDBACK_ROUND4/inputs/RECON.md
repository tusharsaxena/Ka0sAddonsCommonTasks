== (1) Test mode and sim show no Combat Sequence rows (HUD and Results)
F: Nothing in test mode or the sim ever reaches the Combat Sequence. There are three separate gaps. (a) The sample fight is handed to the HUD directly (Hud.OnFightStarted) and never goes out on the bus. CombatLog.Begin only runs on the bus's FIGHT_STARTED, so no capture opens and CombatLog.Window() stays nil. With no window, the drawer's DrawFeed draws only the empty text 'No events yet.' (b) Sample casts are pushed straight into the lane renderer (LaneRender.Push). That skips the LaneCasts listeners, which are what feed CombatLog.OnCast, so the ring never gets a sample line. (c) Sample records (MockFights.Record, used for the test history and the sim's saved fight) are built without `log` or `logTargets`. CombatLog.Of(record) therefore returns nil and the Results section prints 'No combat sequence was saved for this fight'. The data a sequence needs is mostly there already: every plan carries `plan.casts` = { t, spellID, unit 'player'|'pet', interrupted } (MockFights addCast). That maps one to one onto saved lines { t, k=CAST(1), u=1|2, id, f=8 when interrupted }. What is missing is aura data. MockRotations has no buff or debuff fields, so a sample BUFF+/BUFF-/DEBUFF+/DEBUFF- line needs new optional row fields.
FIX: Results (test history and sim fight): in MockFights.Record, add `log` and `logTargets`. Build them by a pure, seeded MockFights.SequenceOf(plan, ident): each plan cast becomes { t, k=1, u=(pet and 2 or 1), id, f=interrupted and 8 or nil }. Then add aura lines from new optional rotation fields, `buff = seconds` and `debuff = seconds`. Retail: Bestial Wrath 19574 and Call of the Wild 359844 as player buffs, Barbed Shot 217200 and Black Arrow 466930 as target debuffs. Forever: Rapid Fire 3045 as a buff, Serpent Sting 25295 as a target debuff. Each one emits BUFF_ON/OFF (k 2/3, u 1) or DEBUFF_ON/OFF (k 4/5, u 3, g 1) at the cast and at the cast plus its duration, clipped to the plan length and sorted by t. `logTargets = { { name = board target name } }`. Set schema to CT_SCHEMA so every Results path (chips with counts, jump-to-cast, caption) works unchanged. HUD (test and sim): add a sample seam to CombatLog in the same style as Results_Source's. CombatLog.UseSample(startT) swaps what Seq/Line/First/Window read to a private sample ring, CombatLog.SampleAppend(at, k, u, id, f) adds lines to it, and CombatLog.EndSample() drops it and restores the live ring. Sim.fightBeat appends the lines falling due at each beat, next to its FeedLanes call (Sim.lua:119). Preview.Stop/Suspend calls EndSample. The seam must also reset the drawer's and the window's feeds (what HudLog's FIGHT_STARTED handler does at Hud_Log.lua:401-404), because that handler never fires for a sample. Tests: one asserting a sample record has a log whose CAST count equals #plan.casts, and one asserting the drawer draws rows in test mode and that EndSample leaves CombatLog.Seq() unchanged.

== (5) HUD min height and the resize model (3+3 minimum, 5+5 default, alternating add and remove)
F: How it works today: the HUD has one fixed height = chrome + stack(hud.bars spell rows) + drawer(sequence.drawer.rows). While the log is docked open, all of the grip's height goes to the sequence rows, and the spell bars are held at hud.bars. Resize bounds are heightFor(bars, 3) to heightFor(bars, 20). While the log is closed or detached, the height goes to the bars only, with bounds MIN_BARS 1 to MAX_BARS 15. On release only one key is stored: sequence.drawer.rows when the log is open, hud.bars otherwise. Defaults are not 5 and 5: hud.bars = 5 but sequence.drawer.rows = 10 (owner feedback item 16), and the chips row is shown. The minimum is therefore 'current bars + 3 sequence rows', and with the log closed it is 1 bar. The large gap in Image #125 is most likely the static height reserving `hud.bars` rows (and the status line) whether or not the fight has that many spells yet. Pixels at the defaults (spell row 18 + 2 gap = 20 px pitch, sequence row 14 px): Spell breakdown section(n) = HEAD_GAP 6 + SECTION_H 22 + (20n - 2) + GAP 8 = 34 + 20n, so 94 px at 3 rows and 134 px at 5. Drawer(r) = GAP 6 + heading 22 + chips (18 + 4 = 22 when shown) + column header 14 + 14r. With chips hidden that is 42 + 14r: 84 px at 3 rows, 112 px at 5. Today's default (10 rows, chips shown) is 204 px. With the 20 px header from item 4, add 6. So 3+3 is 68 px shorter than 5+5 (40 spell + 28 sequence). Removing a sequence row saves 14 px and removing a spell row saves 20 px.
FIX: Defaults: sequence.drawer.rows 10 -> 5 (hud.bars stays 5). Combined with chips hidden (item 6), a new profile opens at 5/5. Minimum: Hud.MIN_BARS 1 -> 3 (HudLog.MIN_ROWS is already 3). Bounds while docked open: lo = heightFor(3, 3), hi = heightFor(15, 20). With the log closed or detached: lo = heightFor(3, 0). Resize model: replace the logTakes either-or with a split. At grip-down, record (b0, l0) = (bars(), HudLog.RowsSetting()). For a dragged height h, find the pair (b, l) reached by walking one row at a time from (b0, l0), and take the last pair whose heightFor(b, l) <= h. Shrinking takes from the larger side (tie: the sequence first), so 5/5 -> 5/4 -> 4/4 -> 4/3 -> 3/3, never below 3 on either side. Growing adds to the smaller side (tie: the spells first), so 5/5 -> 6/5 -> 6/6, until the spells reach 15, after which only the sequence grows, to 20. The walk is monotonic, so it is a short loop over at most 35 steps on plain config numbers. During the drag, feed b to fill()'s v.bars and l to HudLog.SetDragRows. On release, write both hud.bars and sequence.drawer.rows. An old profile with an unequal pair (say 5/10) converges to equal sizes on its first drag, because the larger side gives first. Log closed or detached: as today, the grip moves only the bars (min 3). hud.layout.spells off: the grip moves only the sequence. A new pure function, Hud.SplitFor(h, b0, l0), can be tested headless (5/5 at the default height, 5/4 one sequence row shorter, 3/3 at the minimum, 6/5 one spell row taller). Schema: no step is needed for the rows default unless the owner wants existing profiles to keep 10 (see the question).
Q: (a) Should existing profiles that never changed 'Rows shown' drop from 10 to 5, or be pinned at 10 by a schema step? (b) With the log closed, should the minimum also be 3 spell rows (I recommend yes, for consistency, which raises the Spell bars slider's least value from 1 to 3)?

== (c) The verdict badge: how 'Keep 65' is computed, what 65 means for Peacebloom, where the confidence is shown, and how to restyle it
F: THE SCORE (0-100) adds up points from the item's uses, then clamps the total to 0..100. If the item is new to your collection, the score is 100 and nothing else is counted. Otherwise: QUESTS: +60 for each quest in your log (or ready to turn in) that needs the item; +35 for each quest you can pick up (its minimum level is at most your level + 3); +50 if the item starts a quest; all quest points together are capped at 80. CRAFTING: every KNOWN recipe in a profession you have adds by its skill-up color (orange 30, yellow 20, green 8, gray 0). Every UNKNOWN recipe whose gray level is above your rank adds +10 ('a recipe you could learn'; note that this does not check the recipe's minimum skill). Known and could-learn points together are capped at 50. Separately, each recipe in a profession you don't have adds +3, capped at 9, counted only once your skills have been read. GEAR: +70 for an upgrade, +20 for a sidegrade. DAMPERS: -20 if it is easy to buy again (3 or more vendors, or any vendor at 500 copper or less a unit); -15 if every use it has is gray or done. Then two adjustments: a poor-quality item is capped at 15 unless a quest wants it, and a quest item that no quest counted is floored at 20. THE WORD: Keep at 50 and up; Hold at 20 to 49; under 20, Sell if a vendor buys it, Toss if none does, Hold if the sell price is not known yet. A Low confidence, or gear not yet scored, never says Toss. THE REASONS line shows only the top 2 parts by absolute points (a tie goes to the part counted first: quests are counted before crafting). That is why parts of the score can be invisible. WHAT 65 MEANS FOR PEACEBLOOM: it is Keep (50 or more), 15 points clear of the Keep line. It breaks down as +50 crafting (at the cap) +35 quest -20 easy to rebuy = 65. The data behind it: Peacebloom (2447) is a reagent in 10 Alchemy recipes, 1 Cooking recipe (Peace Tea), 1 First Aid recipe (Minor Healing Potion) and your learned Herbalism recipe Incense Candle. At Alchemy rank 29, Elixir of Minor Defense, Minor Mana, Minor Troll's Blood, Discolored Healing and Spellblasting are orange, and Mana Well, Minor Arcane and Minor Spirit are gray. Known orange recipes are worth 30 each and unknown ones +10 each, so you easily pass the 50 crafting cap. ForeverDB has quest 92109 'My First Alchemy Set' (level 10, minimum 10), which needs Silverleaf, Peacebloom and Empty Vial. You can pick it up, so +35. ForeverDB also lists 3 vendors (Maria Lumere, Hula'mahi, Selina Weston), so -20 for easy to rebuy. Crafting alone could not reach 65: without a quest the maximum is 50 + 9 = 59. The 65 also implies you have Cooking, First Aid and Herbalism ranks, so the 'other professions' +3s are 0. The quest (+35) and rebuy (-20) parts are real but hidden, because only two reasons are shown: the known-recipe note (more than 35 points) and the could-learn note (more than 35 points) outrank the 35-point quest. CONFIDENCE is separate from the score. It measures how much of the needed input was answered, by weight: ForeverDB loaded 3, quest states 3, profession ranks 3, client item info 2, gear verdict 2 (gear only), ForeverDB knowing the item 1. High is 80 and up, Medium 50 and up, otherwise Low. Peacebloom is 12/12 = 100 = High. == (g) Flicker root cause, ranked
F: In plain English: about five times a second the game rebuilds an item tooltip from scratch. It clears it (sometimes hides it as well), refills it, and calls every addon's post call again. On each rebuild DW (a) hides its line the moment the tooltip is cleared or hidden, and (b) tries to put it back by measuring where the blank line is. On a fresh fill the game has not laid out the lines yet, so there is nothing to measure. DW hides the line and puts it back one frame later. The line is therefore missing for one frame in every ten or so, and that is the blink.

H1, very likely (the line above "Drop Watcher"): the hide-on-clear/hide plus measure-in-the-post-call design described above. ItemTree, installed alongside, hit exactly this bug with its own divider and recorded the client mechanics in detail. Its brief TL3: a 50 fps recording showed the rule missing for exactly one frame in ten at the 0.2 s refill, and line FontStrings have no geometry inside the post call. Its BQ3: comparison tooltips are rebuilt about five times a second and have their points taken away first. Its TL2: SetOwner hides a shown tooltip on a bag-slot refill, so a hide hook kills the rule. ItemTree fixed this by hanging its rule from the spacer line with anchors (two invisible edge textures, no measuring) and by keeping a drawn rule through a clear or hide when the same item comes back. DW still uses ItemTree's old, pre-TL3 design.

H2, likely (the second, very dim line in ItemTree's area, same rhythm and same look): it is the SAME DW texture, drawn for a single frame at the wrong height. DW places the line up to three times per rebuild: immediately, on OnSizeChanged, and on the next frame. The first two can read the tooltip's top and the line's position from different, half-finished layout passes. For example, DW's own mid-fill tip:Show() at :780 resizes the tooltip before later post calls (ItemTree's) add their lines. A wrong offset shows for about 1 frame in 10. That duty cycle explains why it is very dim, why it blinks in sync and why it looks identical.

H3, plausible: the dim line is ItemTree's own section rule (MC1, the thin gold-dim line between the materials rows and the price row in its Professions card, which Peacebloom would show). ItemTree's clear and hide hooks take it off on every rebuild (hideStrikes), and it is redrawn by ItemTree's post call. It would blink on the same 0.2 s clock without DW being involved.

H4, unlikely: if DW's post call ran AFTER ItemTree's, ItemTree's keepHintLast (fired by DW's Show and resize) rotates the lines below its hint. DW's stored spacer index would then point one line too low, putting the rule permanently across the "Drop Watcher" label. The owner sees it above the label, so DW's block is probably written first. Both addons register at PLAYER_LOGIN.

Then hang the rule's TOPLEFT and TOPRIGHT from the edges' bottom corners, RULE_INSET in from each side. The client then places the rule in the same layout pass as the line, with no geometry read. Use RuleOffset only for an optional whole-pixel nudge. (2) On OnTooltipCleared and OnHide, do not hide the rule: mark it stale with its item id. The next post call for the same item claims it, and a stale rule nobody claimed comes off on the next frame or when the tooltip shows other data (GetPrimaryTooltipData). (3) Re-check whether the mid-fill tip:Show() at :780 is needed. The client's fill shows after the post calls (TooltipDataHandler.lua:300). The safe prune rule: a stored set is removable only if re-creating it later is lossless and nothing points at it. Keep a set when ANY of these holds: (1) any character's bandSetChoice pick (hostile or friendly) or bandSetAssigned in any stored profile names it; (2) any container's profile field bandSet or bandSetFriendly names it; (3) it has no origin (the player made it from scratch, or the origin is not a preset on this client); (4) it differs from its preset (BandSets.IsModified), OR its name differs from the preset's name, OR any band carries a sound. Diff ignores name and sound, so both need their own check, or a 'modified' set could be lost; (5) it is the last set. Remove the rest: unmodified, unreferenced shipped-preset copies, which are what the old seed added. A character whose class set was pruned gets a fresh identical copy at its first load, so nothing the player made is lost. Note that rule (2) keeps the creator's class set on almost every profile, because every container's field points at bandSetOrder[1].
