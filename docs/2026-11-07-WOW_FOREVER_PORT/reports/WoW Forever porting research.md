# Porting Ka0s to Forever is mostly upstream work

World of Warcraft: Forever (WoW:F, internal codename **Camelot**) is not a Classic client. It is a second game type inside the Retail (Mainline) code family. It launched on **2026-11-04** as client **1.60.1, build 70790**, with TOC interface **16001** and project ID **`WOW_PROJECT_CAMELOT = 18`**. It shares "the vast majority of APIs available in 12.1.5", including Midnight's secret values and the addon lockdown ([Warcraft Wiki: Patch 1.60.1/API changes/notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). For the Ka0s collection that is good news. Each repo can serve both clients with one unsuffixed TOC carrying `## Interface: 120105, 16001`, a single flavour predicate in LibKa0s Compat, and a re-vendor of Ace3 from current master. No separate Forever addons are needed. Most of the work sits upstream of the addons, because the Ka0s standard currently forbids every dual-client shape by name. dev-copilot's interface tooling would collapse a two-number Interface line. The vendored Ace3 stack (CheckBox v26, ColorPicker v28, AceDB MINOR 33) predates every upstream Forever fix. The two conflicts in the notes resolve cleanly. `WOW_PROJECT_ID` is 18 on live; the reading of 1 came from beta builds before about 70170. The `SetDesaturation` break is a Retail 12.1.0 removal that Ka0s shares on both clients, and the fix is a re-vendor of Ace3, not a Compat shim. The real porting risk sits in about seven addons built on systems that Forever hides, reskins or changes: group finder, bank, Encounter Journal, specs, transmog and loot.

## Forever is a Mainline game type with an interface number below Classic's

Blizzard's own statement sets the model: Forever and Midnight are "two game types within the Mainline code family: Camelot … and Standard" ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). It is set in vanilla-era Azeroth with a **level cap of 60**, and it is included with a normal subscription ([Blizzard](http://worldofwarcraft.blizzard.com/en-us/news/24315643/return-to-azeroth-in-world-of-warcraft-forever)). Blizzard's patch server lists it as a separate product, **`wowf`**, at `1.60.1.70790`, beside Retail's `wow` at `12.1.5.70783` ([patch server, wowf](http://us.patch.battle.net:1119/wowf/versions); [patch server, wow](http://us.patch.battle.net:1119/wow/versions)). The two clients share one build counter: they were built on the same day, 82 builds apart. That suggests Forever will keep tracking Retail's mainline code drops, though Blizzard has published no cadence. The owner's install agrees (`/mnt/g/Games/Blizzard/World of Warcraft/.build.info`, `wowf 1.60.1.70790`).

The interface number follows the Retail encoding, 1·10000 + 60·100 + 1 = **16001**. That puts Forever numerically below every Classic flavour except Vanilla (Wrath 30405, Mists 50504), and this is the root of most third-party breakage. Code that reads `GetBuildInfo() >= 100000` as "modern client" sends Forever down Classic paths ([forever-addon-kit](https://github.com/Thunderz96/forever-addon-kit)). Enchantrix, for example, did that and then called the absent `GetNumCrafts` ([Auctioneer-Forever](https://github.com/NoobyGains/Auctioneer-Forever)). Ka0s is immune to this trap today, because no Ka0s-authored code branches on `GetBuildInfo` except diagnostics, perf stamps and DpsRace's records (`LibKa0s/LibKa0s/DebugLogDiagnostics.lua:310-311`, `DpsRace/modules/Recorder.lua:281`).

At the C level, Forever is a near-superset of Retail. Ketho's per-flavour dumps show **181 global functions present only on Forever and 7 only on Retail**, and the 7 were mostly moved into namespaces. Every C_ namespace an Ace3/LibKa0s addon normally touches has an identical function count on both clients: `C_AddOns`, `C_Timer`, `C_Container`, `C_UnitAuras`, `C_TooltipInfo`, `C_LFGList`, `C_LootHistory`, `C_DamageMeter`, `C_CooldownViewer` and `C_Secrets` ([Ketho forever GlobalAPI](https://github.com/Ketho/BlizzardInterfaceResources/blob/forever/Resources/GlobalAPI.lua); [live](https://github.com/Ketho/BlizzardInterfaceResources/blob/live/Resources/GlobalAPI.lua)). The event sets differ by 33 against 3, and every event Ka0s relies on exists on both, including `START_LOOT_ROLL`, `LOOT_HISTORY_UPDATE_*`, `CHAT_MSG_LOOT`, `UNIT_AURA` and `ADDON_RESTRICTION_STATE_CHANGED` ([Ketho forever Events](https://github.com/Ketho/BlizzardInterfaceResources/blob/forever/Resources/Events.lua)). The real differences are elsewhere:

- **Forever-specific frames.** Blizzard ships Camelot copies of FrameXML, so frame chrome, unit frames, the bank, the character frame and the friends window are re-drawn or replaced. Whole Blizzard UI addons are excluded, among them `Blizzard_GroupFinder` (PVEFrame, LFGListFrame), the Encounter Journal, the Challenges/M+ UI, the PvP UI, Garrison and Housing ([Gethe forever AddOns](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns)).
- **Different game rules.** Spec IDs differ (Warrior 1491), and `UnitName` returns a **surname** as its second value ([ForeverPlusPlus](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md)). Character names are region-unique, and the realm key becomes a ruleset ([Ace3 1e98fc00](https://github.com/WoWUIDev/Ace3/commit/1e98fc00)). The bank has 9+9 tab enums but no working Warband bank, plus a keyring at bag −1 ([BetterBags](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)).
- **One shim gated to Retail only.** `Blizzard_DeprecatedSpecialization` is gated `classic, standard`, so `GetSpecialization` and its siblings do not exist on Forever ([Gethe forever](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_DeprecatedSpecialization)).

### Security is Midnight's model, slightly tightened

Blizzard said plainly that "the addon disarmament changes introduced in Midnight, including secrets, will also be active in Forever" ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). The generated API docs carry the same annotations, and in places a few more. `SecretWhenUnitStatsRestricted` appears **63 times on Forever against 50 on Retail**. A Forever-only **`Enum.SecretAspect.FrameStrata`** makes `GetFrameStrata` return a secret for affected frames, and `C_DamageMeter`'s `specIconID` is secret where Retail marks it `NeverSecret` ([forever SecretAspect docs](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretAspectConstantsDocumentation.lua); [forever DamageMeter docs](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/DamageMeterDocumentation.lua)). Creature and pet GUIDs also have their server and spawn IDs obfuscated, and trial accounts cannot send addon messages ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)).

One inference in the local survey needs correcting. It reasons that the Ka0s secret-value guards will be "likely harmless on a client without 12.0 secrets". Forever *has* 12.0 secrets, so those guards stay load-bearing on both clients, and no pre-secrets path should come back. `GetFrameStrata` is called from production code in OutfitterReborn, PanelMaster, PartyFrameEnhanced, PremadeGroupsFilterExtension and QuickComms (local grep). Those call sites need a check that they never compare or save a strata read off a Blizzard frame.

## Two conflicts in the notes resolve on the evidence

### WOW_PROJECT_ID is 18 on live, and 1 was a pre-70170 beta reading

The notes disagree. One reports a beta test on build **69913** where `WOW_PROJECT_ID` returned **1** (`WOW_PROJECT_MAINLINE`) ([wowforeverbuilds](https://wowforeverbuilds.com/news/what-the-wow-forever-beta-breaks-for-addons-secret-health-values-dead-secure-sni)). The first note also concluded that the datamined Lua "contains no `WOW_PROJECT_CAMELOT`". Its search covered only `Blizzard_FrameXMLBase`'s Mists and Cata constants files, and missed a separate addon. The API-diff note found the defining file directly: `Blizzard_ProjectConstants/Camelot/ProjectConstants.lua`, loaded under `[AllowLoadGameType camelot]`, sets **`WOW_PROJECT_CAMELOT = 18` and `WOW_PROJECT_ID = WOW_PROJECT_CAMELOT`** ([Gethe forever ProjectConstants](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_ProjectConstants)).

Three independent accounts give the same timeline. BetterBags records that builds before **70170** reported MAINLINE and 70170 onward reported CAMELOT, which crashed its `isRetail` gate at load ([BetterBags](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)). A community guide observed **1 on 69913 and 18 on 70338** ([wowforeverguides patterns](https://wowforeverguides.com/addons/patterns)). DBM, ElvUI, Dominos, Auctionator and AceGUI ColorPicker v29 all ship code that compares against `WOW_PROJECT_CAMELOT` ([DBM GameVersion.lua](https://github.com/DeadlyBossMods/DeadlyBossMods/blob/master/DBM-Core/modules/objects/GameVersion.lua); [Ace3 e37c055f](https://github.com/WoWUIDev/Ace3/commit/e37c055f)). The two readings therefore describe different builds rather than contradicting each other. The wiki dates the constant to "Patch 1.60.1 (2026-11-04)", which is a launch-date annotation and not the build that introduced it ([Warcraft Wiki: WOW_PROJECT_ID](https://warcraft.wiki.gg/wiki/WOW_PROJECT_ID)). The PartyFrameEnhanced#15 player was on build **70009**, before the switch, so any project-ID evidence from that report is stale.

Two consequences follow for Ka0s:

- Every `WOW_PROJECT_ID == WOW_PROJECT_MAINLINE` gate now **excludes** Forever, and every `~= WOW_PROJECT_MAINLINE` gate sends it down a Classic path.
- `WOW_PROJECT_CAMELOT` is **nil on Retail**, so a headless harness with no `WOW_PROJECT_*` globals evaluates `nil == nil` as true and flags every test as Forever ([BetterBags](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)).

The interface-number fallback that one note proposes (`iface >= 16000 and iface < 17000`) is a step backwards. BetterBags rules it out explicitly, and Bartender4 carries it only as a TODO "until it gets its own project id" ([Bartender4 GameTypes.lua](https://github.com/Nevcairiel/Bartender4/blob/master/GameTypes.lua)). The right predicate is nil-safe and has no interface check: `IS_FOREVER = WOW_PROJECT_CAMELOT ~= nil and WOW_PROJECT_ID == WOW_PROJECT_CAMELOT`, with `IS_MODERN = IS_RETAIL or IS_FOREVER`. One owner `/dump` on live confirms it.

### SetDesaturation is a Retail 12.1.0 removal, so the fix is re-vendoring Ace3

The standard's open evolution records that "`SetDesaturation` is missing [on WoW:F], which breaks every AceGUI checkbox", and the owner's working assumption was that the fix lands in LibKa0s Compat (`WowAddonStandards/standards/standards/open-evolutions.md:349-352`; LibKa0s#44). The evidence points elsewhere. The global `SetDesaturation` appears in the FrameXML **Removed** list for Retail **Patch 12.1.0** ([Patch 12.1.0/API changes](https://warcraft.wiki.gg/wiki/Patch_12.1.0/API_changes)), and **neither** the Forever nor the live UI source defines it today ([Gethe live](https://github.com/Gethe/wow-ui-source/tree/live); [forever](https://github.com/Gethe/wow-ui-source/tree/forever)). Ace3 fixed it upstream on 2026-06-20 in commit 6229eda9, "Fix setting desaturation on WoW 12.1". That commit raised CheckBox from **v26 to v27**, replaced the global call with `check:SetDesaturated(x)`, and shipped in **Release-r1403** ([Ace3 6229eda9](https://github.com/WoWUIDev/Ace3/commit/6229eda9)).

All 17 Ka0s addons vendor a byte-identical CheckBox **v26**, which calls the global at six sites (`PartyFrameEnhanced/libs/AceGUI-3.0/widgets/AceGUIWidget-CheckBox.lua:4,100-130`). **Retail is therefore exposed to the same bug.** The owner probably never sees it because AceGUI registers only the highest widget version (`AceGUI-3.0.lua:553-554`), and any other installed addon that ships v27 silently replaces the Ka0s copy. That mechanism also explains why some Forever players never hit the bug, and why a CurseForge commenter fixed PFE on Forever by "updat[ing] the Ace3 Libraries" (`journal/curseforge/PartyFrameEnhanced/comments.json`, id 8493119). It is an inference that the owner's Retail is masked rather than immune. A `/dump SetDesaturation` on Retail with only Ka0s addons enabled settles it.

The Compat-shim option loses on three counts:

- **It breaks the Compat charter.** A shim would have to install a **global** before AceGUI runs (Questie does exactly this: `SetDesaturation = SetDesaturation or …`, in `_forever_/Interface/AddOns/Questie/Modules/QuestieCompat.lua:1305-1316`). LibKa0s Compat publishes a library table, not globals, and is deliberately narrow (`LibKa0s/LibKa0s/Compat.lua:16-34`).
- **It fixes only one of the stale widgets.** The same vendored stack has **ColorPicker v28**, which inverts alpha on Forever (`INVERTED_ALPHA = (WOW_PROJECT_ID ~= WOW_PROJECT_MAINLINE)`, `PartyFrameEnhanced/libs/AceGUI-3.0/widgets/AceGUIWidget-ColorPicker.lua:16`). Ace3 fixed that in ColorPicker v29 ([Ace3 e37c055f](https://github.com/WoWUIDev/Ace3/commit/e37c055f)).
- **It misses AceDB.** The vendored **AceDB MINOR 33** predates the Forever character and realm keys that arrived in MINOR 36–40 ([Ace3 ac3d1225](https://github.com/WoWUIDev/Ace3/commit/ac3d1225)).

The verdict is to **re-vendor Ace3 at or after ac3d1225 (2026-10-28)**, which needs no edit to any vendored file, and to drop the Compat shim. There is one catch. The ColorPicker and AceDB fixes sit on Ace3 master; no tag after r1403 carries them yet ([Ace3 commits](https://github.com/WoWUIDev/Ace3/commits/master)). The owner must choose between vendoring a master commit and waiting for a tag. Timing matters for AceDB. Forever SavedVariables live in a separate `_forever_\WTF`, so Retail data cannot collide. But if Ka0s ships a Forever build on MINOR 33 and upgrades later, every Forever player's character profile key changes under them, so the re-vendor must land **before** the first Forever release.

## One TOC with two numbers works on the client and the packagers

The client side is settled. Forever loads `_Forever.toc` or `_Camelot.toc` first, then the family file `_Mainline.toc`, then the plain `Addon.toc`. Comma-separated Interface lines have worked since 10.2.7, and the wiki's own example is `## Interface: 120105, 16001, 50504, 11509` for "retail, forever, classic, and classic era" ([Warcraft Wiki: TOC format](https://warcraft.wiki.gg/wiki/TOC_format)). A Retail-only `120105` marks the addon out of date on Forever. Every Ka0s addon today ships exactly one unsuffixed TOC with a single `## Interface: 120105` and no workflow files (local survey), so the minimal change is literally appending `, 16001`. Ace3, BigWigs, Bartender4, Dominos, Masque and DBM all use this single-TOC pattern ([Ace3.toc](https://github.com/WoWUIDev/Ace3/blob/master/Ace3.toc); [Bartender4.toc](https://github.com/Nevcairiel/Bartender4/blob/master/Bartender4.toc)).

Suffixed TOCs bring three hazards that the single TOC avoids:

- **The client and the packager disagree on suffixes.** The client accepts `_Forever` as an alias of `_Camelot`. The BigWigs packager's suffix regex recognises `_Camelot` but **not `_Forever` or `_Standard`** ([packager release.sh](https://github.com/BigWigsMods/packager/blob/master/release.sh)).
- **The suffix may be renamed.** The wiki warns that "the Camelot value may be changed to Forever in the future" ([TOC format](https://warcraft.wiki.gg/wiki/TOC_format)).
- **The fallback order is disputed.** One author reported that Forever did *not* fall back to `_Mainline` and that the order changed between builds ([cdtl3-dev PR #1](https://github.com/Nelnamara/cdtl3-dev/pull/1)), against the wiki's documented model.

Inline file directives cover Forever-only or Retail-only files without suffixes. A line such as `Compat\Forever.lua [AllowLoadGameType forever, camelot][ExcludeLoadGameType standard]` lists both names to survive the rename and adds the Exclude because "if none of the game types are recognized … the condition will be satisfied" ([TOC format](https://warcraft.wiki.gg/wiki/TOC_format)). One trap is worth recording in the standard. An addon-level `## AllowLoadGameType: standard` means Midnight only and **excludes** Forever, while `mainline` includes it. The same distinction applies inside Lua: "Retail" now has to mean either "Standard only" or "Modern (Standard + Forever)".

### Packaging and CurseForge

On CurseForge, Forever is its own game-version type, **88568**, at version 1.60.1; Retail is type 517. A single file becomes dual-flavour by carrying version IDs from both types, and the project then lists as "Retail +1" ([release.sh](https://github.com/BigWigsMods/packager/blob/master/release.sh); [NaowhForever #248](https://github.com/naowh-gaming/NaowhForever/pull/248)). Wago lists Forever as `forever`, at patch 1.60.1 ([Wago API](https://addons.wago.io/api/data/game)), and WoWInterface has no Forever type. The BigWigs packager v2.7.0 handles all of this from one multi-interface TOC ([packager README](https://github.com/BigWigsMods/packager/blob/master/README.md)).

The open question for Ka0s is narrower. The repos have no `.github/workflows` and release through **CurseForge's own tag-triggered packager**. No primary source says how that packager maps a comma list or 16001; its multi-TOC article predates Forever ([CurseForge support](https://support.curseforge.com/support/solutions/articles/9000209856-multi-toc-for-world-of-warcraft-addons)). Other projects do get "Retail +1" tags, but their PR does not say which packager they use. The cheap test is one alpha tag on a shell-only addon, followed by a look at its Files tab. CurseForge lets authors edit file tags by hand if the mapping fails. The journal needs no change, because `curseforge_journal.py` records `gameVersions` verbatim (`~/.claude/plugins/cache/dev-copilot/dev-copilot/2.7.1/scripts/curseforge_journal.py:478`). No speculative number such as 16002 should ever be listed: an unknown version can fail the upload ([guildos #20](https://github.com/danielcosta42/guildos/issues/20)).

### Knowledge bases to treat as normative

The authoritative references divide by job:

- **warcraft.wiki.gg** sets the rules. Its TOC format page and the 1.60.1 API-change notes transcribe Blizzard's WoWUIDev Discord posts ([TOC format](https://warcraft.wiki.gg/wiki/TOC_format); [API changes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes)).
- **Gethe/wow-ui-source `forever`** is the FrameXML ground truth, current to 70790 ([Gethe forever](https://github.com/Gethe/wow-ui-source/tree/forever)).
- **Ketho/BlizzardInterfaceResources `forever`** is the source for global, event and atlas diffs. It is about two weeks stale, at 70532 ([Ketho forever](https://github.com/Ketho/BlizzardInterfaceResources/tree/forever)).

Ketho's vscode-wow-api has no Forever flavour; its last commit was 2026-06-24 ([vscode-wow-api](https://github.com/Ketho/vscode-wow-api)). Blizzard publishes no developer documentation of its own outside Discord. Beta-era community kits predate builds 70170 and 70291 and are partly stale ([forever-addon-kit](https://github.com/Thunderz96/forever-addon-kit)). The standard's FrameXML citations point at Gethe's `live` branch only, so a Forever-aware standard should cite both branches.

## What each layer of the collection must change

The standard (v2.102.2) is **explicitly Retail-only**, and it bans both viable shapes by name: "comma-separated multi-flavor" Interface lists and "per-flavor TOC files" (`WowAddonStandards/standards/standards/toc-file.md:57-65`). It also forbids `WOW_PROJECT_ID` branching and limits Compat to "Retail patch differences — not across game flavors" (`compat.md:5,42`). Every other layer inherits those rules, so the standard ruling comes first.

### Per-addon exposure

Per-addon risk splits into three tiers:

- **Shell-only.** AbsorbTracker, PanelMaster, PrettyChat and LibKa0sSkinTester should port with the TOC line and the Ace3 re-vendor alone. PFE#15 and its CurseForge commenter show that this is enough to run a Tier 2 shell on Forever.
- **Moderate.** ConsumableMaster, AuraMaster, QuickComms, PartyFrameEnhanced and WhatGroup have API-level risk: spec-ID tables, chat and comms restrictions, strata reads, and PFE's Edit Mode hooks against Forever's extra `Enum.EditModeSystem` members ([forever EditMode docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)).
- **Feature-level risk.** These addons depend on systems Forever changes, so the source has to be checked against Forever behaviour one addon at a time.

|---|---|---|
| PremadeGroupsFilterExtension | `Blizzard_GroupFinder` (PVEFrame, LFGListFrame) has `ExcludeLoadGameType: camelot`, and Forever substitutes a Vanilla-style LFG UI. No M+ exists. | Likely Retail-only via TOC gate, or a new UI integration |
| BankLedger, LootHistory | 9+9 bank tab enums, no Warband bank in practice, no `Enum.BagIndex.Bank` ([BetterBags](https://github.com/Cidan/BetterBags/blob/HEAD/.claude/rules/camelot-forever.md)) | Enum-driven sizing, Warband features gated off |
| DropWatcher | Encounter Journal not loaded, `EncounterJournalDisabled` rule reported, transmog reported disabled. Camelot loot rules undocumented. | Gate `CompatJournal`/transmog off; test loot rolls in game |
| MultiMeters, DpsRace | `C_DamageMeter` and `Blizzard_DamageMeter` load on camelot, but `specIconID` is secret | Port; secret-guard the spec icon |
| KickCD | `C_CooldownViewer`, `C_CurveUtil` and `C_DurationUtil` present; the Cooldown Manager was enabled per class during beta ([dev notes 09-24](https://us.forums.blizzard.com/en/wow/t/wow-forever-beta-development-notes-%E2%80%93-updated-september-24/2360696)) | Port; verify per class in game |
| OutfitterReborn | Camelot `CharacterFrame`, different talents and specs, transmog off, `EquipmentManager_UnpackLocation` absent | Port with care; `C_EquipmentSet` on Forever unverified |

A local grep found only three two-value `UnitName` captures in production code, any of which would read a surname as the realm on Forever: `DropWatcher/core/Compat.lua:883`, `LootHistory/core/Compat.lua:980` and `OutfitterReborn/modules/Triggers_Params.lua:321`. Two of the three query the `"NPC"` unit, which does not affect a player's identity, so the exposure is small. Any per-character or per-realm keys derived from player names need the same review AceDB went through.

## Conclusion

The port should run as a cross-repo bundle in dependency order:

1. **The owner's ten-minute `/dump` pass.** It turns the inferences above into facts before anything is written.
2. **A WowAddonStandards ruling** that reframes the collection from "Retail only" to "Modern (Standard + Forever)". It admits one dual-number TOC and one Compat flavour predicate, and bans everything else that multi-flavour support usually drags in.
3. **LibKa0s and dev-copilot changes.** These are the Compat predicate, the kit's Forever profile, and the bump, review and scaffold tools.
4. **An Ace3 re-vendor across all 17 addons.** This closes LibKa0s#44's SetDesaturation thread on Retail as well, whether or not Forever ever ships.
5. **The addon tiers.** Shell-only addons go first, with one alpha tag to prove CurseForge tagging, then moderate, then feature-level.

The reframing to "Modern" is the less obvious payoff. Forever is already ahead of Retail in places, such as the FrameStrata secret aspect and its extra stat restrictions. A collection that passes on both clients is effectively pre-testing Retail 12.2.

Not every addon should be forced across. PremadeGroupsFilterExtension extends a Blizzard frame that Forever does not load, and Ka0s addons built on M+, the Warband bank or the Encounter Journal would ship features with nothing to act on. The single-codebase goal still holds for them. A Forever build of such an addon is the same repo with its features gated off, or with `16001` left off its Interface line. That choice is recorded per addon in the bundle, and neither option forks the repo.
