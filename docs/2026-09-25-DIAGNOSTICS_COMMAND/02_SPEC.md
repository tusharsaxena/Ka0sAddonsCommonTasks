# Spec

The target end state. It is not a schedule (that is `03_EXECUTION_PLAN.md`). Requirement IDs:

- `STD-nn`: the rule text in WowAddonStandards (debug-logging-§14 and its ripple)
- `AP-01`, `AUD-01`: the anti-pattern and the audit check
- `LIB-nn`: the LibKa0s helper and Slash change
- `BUF-nn`: the buffer change and its measurement gate
- `DX-<ADDON>`: per-addon report content contracts
- `X-nn`: the DragHandle close behavior per host (ruled, Q1 in `OWNER_RULINGS.md`; recorded as DR-OW-03)

Where a requirement depends on an open question, it names it (`Q<n>`, see `04_OPEN_QUESTIONS.md`) and
is written in the form the owner ruled (`OWNER_RULINGS.md`, 2026-09-26).

## 1. The standard: debug-logging-§14 "The diagnostics dump" (MUST)

Appended as a new section so existing numbers stay stable. Standard version **v2.68.0** (Q5).

| ID | Requirement |
|---|---|
| **STD-01** | Every Ka0s addon **MUST** ship a diagnostics dump. It is not optional for small addons. |
| **STD-02** | **Exactly two forms** run it: `/<slash> diagnostics` (an `NS.COMMANDS` row) and `/<slash> debug diagnostics` (a word of the `debug` verb). The addon's slash alias (for example `/auramaster`) works with both, as it does with every verb. |
| **STD-03** | The `debug` handler tests `diagnostics` **first**, before `on`/`off` and before the window toggle or usage fallback. Matching is case-insensitive. |
| **STD-04** | **No other verb or word runs the report.** No `diag`, `dump`, `dx` or any other alias, neither as a `COMMANDS` row, a debug word, nor a Slash-descriptor `aliases` entry. An unknown debug word does whatever that addon already does with unknown words (toggle, or usage). A retired name (`diag`, `dump`) becomes an ordinary unknown word: no hint, no special case, because the owner ruled out any short alias such as `diag` and a word the dispatcher still recognizes is one step from being one (Q7, recommended (a); a hint line exists only if the owner rules Q7(b)). |
| **STD-05** | **Works while the addon is disabled or stood down.** `diagnostics` is a reserved verb on the live list (slash-commands-§2/§7). The report reads state only: it **MUST NOT** take or release a Lifecycle hold, register an event, arm a timer, or stand anything up. While stood down it still runs every section; sections whose runtime state is released print that they are stood down instead of empty data (Q4). |
| **STD-06** | **Ungated sink.** Lines go to the debug console through the ungated `Add` path (`NS.DebugLog:RunDiagnostics`, LIB-01). The report never reads or changes the debug-logging flag, and it lands with logging off. |
| **STD-07** | **Appends, never clears.** Nothing reachable from the report calls `Clear()`. The trace the player just reproduced stays above the report, so one Copy carries both. |
| **STD-08** | **Markers.** First line `[Diag] ==== <BrandName> diagnostics begin ====`. Last line `[Diag] ==== <BrandName> diagnostics end: N line(s) ====`, where N counts every report line including both markers. `<BrandName>` is the addon's full brand (for example `Ka0s Aura Master`) (Q9). |
| **STD-09** | **Reveal and one chat line.** If the console is hidden, the report shows it. Then it prints one localized, tagged chat line with the line count that names Copy. README step 3 remains correct as the fallback. |
| **STD-10** | **Content contract.** In order: (a) the begin marker; (b) the **identity header**: brand and version, schema version (stored and code), active profile (or "account-wide" for global-only addons), client build (`GetBuildInfo`: version, build, interface), locale, the **running** LibKa0s minors (`LibKa0s-Core-1.0`'s `MODULES` table; under LibStub the running copy may come from another addon's vendor, so the report labels them "running", and there is no runtime release string to print), and state flags: stored-enabled, stood-down, Lifecycle holds, debug flag, test mode where the addon has one, `InCombatLockdown()` and `UnitAffectingCombat("player")`; (c) **settings that differ from their defaults**, each as `path = value (default)`, walked over the addon's Schema, plus the addon's named always-print rows; (d) **domain state**: the addon's own sections (`DX-*`); (e) rejected events and any error record the addon keeps; (f) the `truncated` line when a cap bit; (g) the end marker. Nothing is redacted, because users send the report to the owner privately. (Q11) |
| **STD-11** | **Plain text.** Color, texture, atlas and hyperlink escapes are stripped, so the Copy text is clean. A value whose escapes are the evidence (PrettyChat format strings) is rendered with `|` doubled to `||`, which pastes back into `/<slash> set` unchanged. |
| **STD-12** | **Secret-value safe (Midnight 12.x, events-frames-taint-§8).** Every value is stringified through `SafeToString` before any format sees it; formats are `%s`-only on pre-stringified arguments; every number is tested readable before arithmetic or comparison; no API known to raise on a secret is called while values are secret; every section runs under its own `pcall`, so a raise costs exactly one line `section <name> failed: <err>`. The report is read-only and calls no protected API, so it is safe in combat. Sections that cannot read in combat say so (`unreadable in combat`). |
| **STD-13** | **English body.** Report body lines are English diagnostic text and do not go through `NS.L`, like trace lines. The one chat line, and a hint line if the owner rules Q7(b), are localized. |
| **STD-14** | **Library absent.** The DebugLog stub's `RunDiagnostics` prints the collection's existing placeholder, `L["%s is unavailable: the LibKa0s library did not load."]` with `%s = "/<slash> diagnostics"`, writes nothing and returns 0. |
| **STD-15** | **Capped below the console buffer.** Total lines stay at or under `lib.DIAG_MAX_LINES` (library-owned, clamped to `lib.MAX_BUFFER - 100`). Unbounded lists carry per-list caps (default 40 ids, host may set per list). A capped report still ends with the end marker; the `truncated: N line(s) omitted, per-list caps hit=yes|no` line precedes it. The report is guaranteed whole in the console; the trace ahead of it is best effort. |
| **STD-16** | **Built on the library helper** (`LibKa0s-DebugLog-1.0` minor 14 with DebugLogDiagnostics, vendored LibKa0s ≥ v1.60.0). The host writes sections only. It **MUST NOT** hand-roll the line buffer, per-section pcall, markers, cap or the Add loop (anti-pattern #47 and #90). |
| **STD-17** | **README.** documentation-§1 gains item 9, `## Reporting a bug` (MUST), between `## Troubleshooting` and `## Issues and feature requests`. Its body is exactly the following, with the addon's real slash (never `<slash>`). It names no destination and carries no GitHub or issues link: |

```markdown
## Reporting a bug

1. Type `/<slash> debug on` and reproduce the bug.
2. Type `/<slash> diagnostics`.
3. If the debug window isn't open, open it with `/<slash> debug`. Press **Copy**, copy the entire output, and include it with your bug report.

The report is added after the debug trace in the same window, so one copy carries both.
```

| **STD-18** | The README's Troubleshooting table SHOULD carry a row "Something looks wrong and I want to report it → Follow [Reporting a bug](#reporting-a-bug) below." Rows that told players to paste logs another way point at the section instead. The section and the row go through the de-AI pass like any README edit. |
| **STD-19** | **Suite case.** Every addon's suite asserts: both markers present; pre-existing console lines survive (append); with the debug flag off the lines land and the flag is unchanged; the report runs while disabled through **both** forms; a raising section costs exactly one line; an over-cap report ends in `truncated` then the end marker; a secret mock does not raise; `debug diag` (and the addon's retired names) do not run the report. ## 2. Anti-pattern and audit check

**AP-01** (anti-pattern #90):

> 90. **A diagnostics dump that is missing, aliased, gated or destructive.** No `/<slash> diagnostics` or
> no `/<slash> debug diagnostics`; a `diag`, `dump` or other alias that runs the report; the report written
> through the gated sink, so a run with logging off writes nothing; a `Clear()` before the report, which
> erases the trace the player just reproduced; a report refused while the addon is disabled; an uncapped
> report that evicts the trace ahead of it; a host-written line buffer, pcall wrapper and marker set in
> place of `LibKa0s-DebugLog-1.0`'s helper (debug-logging-§14, slash-commands-§2).

**AUD-01** (AUDIT.md step 4, next to the enable/disable check):

1. `grep -n '"diagnostics"' settings/*.lua core/*.lua` hits exactly one `COMMANDS` row, and the debug
   handler tests `diagnostics` before its other words.
2. `grep -rniE '"(diag|dump|dx)"' settings core modules` is empty in `COMMANDS`, in debug-word tables
   and in the Slash descriptor's `aliases`. A hit that is a separate topic dump (not the report) is noted,
   not failed.
3. `diagnostics` is live while disabled: the host passes no `liveVerbs` (Slash minor ≥ 16 default), or its
   `liveVerbs` is built on `SlashLib.LIVE_VERBS`. `tests/test_disabled.lua` dispatches both forms.
4. Both forms reach `NS.DebugLog:RunDiagnostics`; no `:Clear()` is reachable from the sections module.
5. The DebugLog stub answers `RunDiagnostics` with the library-absent line.
6. README has `## Reporting a bug` between `## Troubleshooting` and `## Issues and feature requests`, with
   the three steps and the note verbatim for this slash.
7. Grading: a missing form, an alias, a gated sink, a clear or a missing README section is a MUST
   failure. A host-written buffer/markers/pcall on a vendor ≥ v1.60.0 is #47/#90.
8. Applicability: the check runs in the eleven addons only. LibKa0s is audited against library-stack-§7's
   list (STD-24 updates its debug-logging row), and WowAddonStandards and wow-addon against
   documentation-§8's list, which already exempts debug-logging (`documentation.md:665`).
